# Helel pre-manual-testing action plan

Plan date: 2026-09-11

## Current truth

Helel v0.1 is a buildable local developer preview. The editor, workspace tools, Git inspection, process runner, repository index, deterministic session state, dataset/tokenizer pipeline, model architecture, local inference protocol, and release checks exist and pass automated verification.

Helel is not yet a Codex- or Claude-like coding agent. The current agent follows a fixed scripted sequence, the indexer is lexical, no useful Helel-46M weights exist, the MLX process is not packaged with the app, and the desktop does not yet route model proposals through the Rust agent executor. Full manual product testing should begin only after the P0 work below.

## Missing capabilities

### P0 — required before full manual testing

1. **Real agent orchestration**
   - Replace the fixed search → Git → `cargo test` sequence with a bounded loop.
   - Support plan, inspect, edit, run, observe, retry, verify, complete, pause, and cancel.
   - Add limits for steps, wall time, generated bytes, tool failures, and repeated actions.
   - Persist the complete event log and resume interrupted sessions.
   - Acceptance: a scripted planner can complete create/edit/test tasks in disposable repositories without special-case code.

2. **Model runtime inside the desktop**
   - Add a model-artifact picker and validate tokenizer, config, weights, quantization, and checksums.
   - Package or locate an MLX sidecar without relying on a developer `PYTHONPATH`.
   - Start, health-check, restart, and stop the runtime from Rust.
   - Stream tokens and structured proposals into the desktop.
   - Keep deterministic mode available when no weights are installed.
   - Acceptance: the packaged app can load a compatible local smoke checkpoint on a clean Mac and return a constrained proposal with networking disabled.

3. **Model proposal → Rust tool bridge**
   - Decode the versioned proposal in Rust.
   - Validate every argument again at the trusted boundary.
   - Convert accepted proposals to existing `ToolRequest` values.
   - Require per-action approval for writes, processes, Git mutations, and patches.
   - Reject unknown fields, oversized values, stale session IDs, and replayed proposals.
   - Acceptance: hostile and malformed model output cannot execute a command or change a file.

4. **Transactional edit and rollback flow**
   - Create a task checkpoint before the first mutation.
   - Preview diffs before approval.
   - Apply multi-file patches atomically.
   - Restore the exact pre-task state after failure or user rollback.
   - Handle dirty user buffers explicitly.
   - Acceptance: forced failures at every mutation boundary leave the repository recoverable and preserve unrelated user changes.

5. **Project-aware command and verification policy**
   - Detect Rust, Node/pnpm/npm, Python, Java/Maven/Gradle, Angular, React, and Flutter projects.
   - Select build, lint, test, and format commands from checked-in project metadata.
   - Classify package scripts and build hooks as code execution.
   - Show the exact command, working directory, timeout, and risk before approval.
   - Acceptance: fixture projects for every supported stack run the correct offline-safe validation command.

6. **HelelBench**
   - Build disposable repositories with deterministic tasks and validators.
   - Start with at least 30 tasks: 10 code edits, 5 repairs, 5 tests, 5 refactors, and 5 full-stack scaffolds.
   - Record success, build/test result, valid tool-call rate, rollback success, actions, runtime, and crashes.
   - Preserve every discovered failure as a regression case.
   - Acceptance: the scripted agent passes infrastructure tasks reliably; learned-model scores are reported separately.

7. **Reliable filesystem, terminal, and Git behavior**
   - Replace 2.5-second tree polling with native watching and editor conflict notices.
   - Add a PTY terminal with resize, input, cancellation, and bounded output history.
   - Add Git stage, commit, checkpoint, restore, and task-diff APIs.
   - Persist security audit records rather than resetting on exit.
   - Acceptance: external edits, long-running commands, terminal input, and rollback survive adversarial integration tests.

8. **Compiler-grade repository intelligence**
   - Replace lexical parsing with Tree-sitter or language-server-backed parsing.
   - Store files, symbols, references, diagnostics, and index versions in SQLite/FTS5.
   - Incrementally handle create, modify, rename, and delete events.
   - Add exact definition/reference lookup and ranked context budgets.
   - Acceptance: symbol/reference fixtures cover Rust, TypeScript/JavaScript, Python, and Java with no stale records after mutations.

### P1 — required before calling v0.1 broadly usable

9. **Framework skills**
   - Add versioned skills for React, Angular, Spring Boot, Python services, and full-stack React/Spring and Angular/Spring projects.
   - Each skill defines detection, conventions, commands, file boundaries, validation, common failures, and fixture tasks.
   - Flutter follows after the first five stacks are stable.

10. **Desktop agent experience**
    - Replace the duplicate right-panel placeholder and sidebar-only controls with one coherent task workspace.
    - Show plan, current action, context used, tool request, approval reason, live output, diff, tests, and final report.
    - Add pause, resume, stop, rollback, retry, and export-log controls.
    - Make all controls keyboard accessible and screen-reader labeled.

11. **Useful model weights**
    - Approve a production source registry and data policy.
    - Build, inspect, and freeze train/validation/test manifests.
    - Train Helel-22M first as an end-to-end quality baseline.
    - Train Helel-46M only after 22M learning curves and evaluations are healthy.
    - Compare full precision, int8, and int4 on identical held-out tasks.
    - Publish a model card with data lineage, limitations, metrics, hardware, energy, and checkpoint checksum.
    - This is not realistically FOC at meaningful quality unless existing owned hardware and electricity are treated as sunk costs.

12. **Cross-platform release validation**
    - Add Windows and Linux CI/build hosts.
    - Replace or complement MLX with a portable inference backend.
    - Build signed/notarized macOS, signed Windows, and packaged Linux installers.
    - Test clean install, update, uninstall, paths with spaces/Unicode, permissions, and offline startup.

### P2 — advanced features after the first manual-testing cycle

- LSP completion, hover, rename, code actions, formatting, and debugger integration
- Multi-root workspaces and worktree-per-task isolation
- Long-term project memory with explicit inspect/delete controls
- Parallel read-only subagents and serialized mutations
- Visual test explorer, coverage, and benchmark dashboards
- Project templates and dependency-aware scaffolding
- Native Rust/C++ quantized inference with KV cache and speculative decoding
- Extension/skill marketplace with signed local packages
- Sandboxed command execution using platform-native isolation
- Accessibility certification, localization, crash recovery, and update channels

## Recommended execution order

| Wave | Work packages | Exit gate |
| --- | --- | --- |
| 1 | HelelBench, project fixtures, project-aware verification | At least 30 deterministic benchmark tasks execute and score reproducibly |
| 2 | Transactional edits, Git checkpoints, persistent audit, native watcher, PTY | All failure-injection and rollback tests pass |
| 3 | Real agent loop and model-proposal Rust bridge | Scripted planner completes multi-step tasks under budgets |
| 4 | Compiler-grade index and framework skills | Supported-stack symbol and build fixtures pass |
| 5 | Packaged local runtime and smoke weights | Clean-machine offline model proposal succeeds |
| 6 | Desktop agent workspace and accessibility | A user can inspect, approve, pause, resume, cancel, and rollback every task |
| 7 | Approved data and Helel-22M/46M training | Held-out quality and quantization gates pass |
| 8 | Full manual testing and cross-platform packaging | No open P0 defect; release checklist is signed off |

Do Waves 1–4 before spending substantial time on model training. They make failures measurable and let the same agent infrastructure work with scripted planners, weak early checkpoints, and stronger later checkpoints.

## Definition of ready for full manual testing

All of the following must be true:

- `python3 scripts/verify.py` passes from a clean checkout.
- HelelBench contains at least 30 versioned tasks and produces a machine-readable report.
- Scripted-agent task success is at least 95% on deterministic infrastructure cases.
- Invalid tool-call rejection is 100% across the adversarial contract suite.
- Rollback restores the pre-task state in every failure-injection case.
- No P0 security, data-loss, crash, or repository-escape defect is open.
- The app runs for two hours of mixed editing and agent tasks without an unrecovered crash.
- A clean Mac can install and run the app offline.
- If learned planning is tested, the exact local model/tokenizer checksums are recorded.
- Manual testing uses disposable repositories or committed branches until rollback has proven reliable.

## Manual test matrix

Test these scenarios only after the readiness gate:

1. **Existing repository edits:** add validation, repair a defect, refactor duplication, add tests, update documentation.
2. **New projects:** React app, Angular app, Spring Boot API, Python service, React/Spring full stack.
3. **Failure recovery:** compile errors, failing tests, missing dependency, cancelled command, malformed patch, app restart, runtime crash.
4. **Security:** path traversal, symlink escape, prompt injection in source files, malicious package scripts, oversized output, replayed approval.
5. **User-state safety:** dirty buffers, external edits, renamed files, untracked files, partial Git state, rollback with unrelated changes.
6. **Performance:** 1K, 10K, and 20K-file repositories; long files; repeated indexing; 2K-context generation; int4 model startup.
7. **Usability:** keyboard-only task, screen reader labels, understandable approvals, visible progress, useful final report.

For every manual failure, save the repository fixture, task prompt, model checksum, event log, expected behavior, and validator as a new HelelBench regression test.

## How to use Codex or Claude to build the remaining work

### Working rules

- Give one bounded work package to one task/thread.
- Use a new Git worktree or branch for risky or parallel work.
- Keep `AGENTS.md` short; put scope and acceptance criteria in an execution-plan file.
- Ask the agent to inspect before editing and to continue until every acceptance criterion passes.
- Never ask “implement all advanced features.” Split work into slices that take roughly one focused review.
- Require evidence: changed files, tests, benchmark delta, risks, and remaining limits.
- Use a separate review task after implementation for security-critical changes.
- Merge only from a clean diff after the top-level verification gate passes.

### Prompt to create the next execution plan

```text
Read AGENTS.md, docs/architecture/, docs/ROADMAP.md, all phase audits, and
docs/product/PRE_MANUAL_TESTING_PLAN.md.

Create a detailed execution plan for Wave 1, Slice 1: the HelelBench harness.
Do not implement it yet.

The plan must include:
- exact scope and explicit non-goals
- repository files and public contracts involved
- fixture format and validator design
- security and cleanup behavior
- ordered implementation steps
- objective acceptance criteria
- exact validation commands
- rollback/migration considerations
- risks and follow-up slices

Save it as docs/exec-plans/active/P11-S01-helelbench-harness.md.
```

### Prompt to implement one slice

```text
Read AGENTS.md and docs/exec-plans/active/P11-S01-helelbench-harness.md.
Inspect the existing implementation and relevant architecture before editing.

Implement the plan completely. Stay inside its scope. Preserve the offline,
FOC, workspace-boundary, approval, and no-hosted-LLM constraints.

Run every validation command in the plan and then run:
CARGO_NET_OFFLINE=true python3 scripts/verify.py

Do not claim completion if a check fails. Update architecture and audit docs
when the implemented boundary changes. Finish with:
1. behavior added
2. files changed
3. tests and benchmark results
4. security impact
5. known limitations
6. exact next slice
```

### Prompt for an independent review

```text
Review the current branch against:
- AGENTS.md
- docs/exec-plans/active/P11-S01-helelbench-harness.md
- docs/architecture/security.md

Do not modify code initially. Find correctness, data-loss, security,
cross-platform, determinism, performance, and test-coverage problems.
Rank findings P0–P3 with exact file and line references.

After the review, fix every P0/P1 finding, add regression tests, run the plan's
validation commands and the full repository verification, then report any
remaining P2/P3 items separately.
```

### Prompt for converting a manual failure into a regression

```text
This manual Helel task failed.

Task prompt: <paste prompt>
Expected behavior: <describe>
Observed behavior: <describe>
Model/checkpoint checksum: <checksum or deterministic planner>
Event log: <path>
Disposable repository: <path>

Reproduce the failure without modifying the original fixture. Add the smallest
HelelBench case that fails for the same reason, identify the owning subsystem,
fix the root cause, and prove the new regression and full verification pass.
Preserve unrelated behavior and document any changed security boundary.
```

## Codex-specific workflow

1. Open the Helel repository as a Codex project.
2. Start each slice in a worktree so Codex does not disturb the stable checkout.
3. Paste the implementation prompt with the exact plan path.
4. Let Codex run tools and checks; answer approval requests only after reviewing the exact command or mutation.
5. Ask a second Codex task to review the branch when the slice touches paths, commands, patches, approvals, persistence, model parsing, or release code.
6. Review the diff and benchmark output in the app, then merge the worktree branch.
7. Turn any discovered defect into the next regression slice.

## Claude Code-specific workflow

1. Start Claude Code from a dedicated Git worktree for the slice.
2. Put the same plan path in the first prompt; Claude should use repository files as the source of truth.
3. Keep permission mode conservative for shell commands and file writes.
4. Require the exact top-level verification command before accepting completion.
5. Use a fresh Claude session for independent review so it does not inherit the implementer's assumptions.
6. Inspect every proposed command that installs dependencies, accesses the network, changes Git history, signs artifacts, or touches files outside the worktree.

Codex and Claude are development tools for building Helel. If the production requirement remains “no external AI service,” do not embed either service or API into the shipped application. Code they author becomes part of the repository; runtime requests from Helel users must stay with the local Helel model.
